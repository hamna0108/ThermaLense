NOVATORE SOLUTIONS Neural PDE Solver &amp; Digital Twin with Inverse Physics Owner: Hamna Mehmood Advanced 8-Week Capstone Brief 1. Assignment Summary Owner Hamna Mehmood Project Neural PDE Solver &amp; Digital Twin with Inverse Physics Primary Domain Scientific Machine Learning, PINNs, Neural Operators &amp; Inverse Problems Duration 8 weeks Working Style Research + engineering capstone; a demo alone is not completion Final Evaluation Code freeze + hidden benchmark + technical viva Project premise. Build a scientific digital twin for a physical field problem. Start from a trustworthy numerical solver, then learn the solution with a physics-informed neural network and a neural operator, infer unknown physical parameters from sparse/noisy sensors, and detect when observations are inconsistent with the modeled physics. Primary research question. Can a learned physics model generalize across unseen boundary conditions and infer hidden parameters from sparse/noisy measurements while approaching a trusted numerical solver and providing useful fault/anomaly signals? 2. Learning &amp; Engineering Objectives Understand the governing PDE and implement a numerical reference solution before training ML. Train and stabilize a physics-informed neural network with explicit PDE/boundary/initial losses. Solve an inverse problem by estimating unknown physical parameters from sparse sensors. Train a neural operator (FNO, DeepONet or equivalent) over a family of boundary/parameter settings. Study sparse sensor placement and measurement-noise robustness. Use physics residuals/model disagreement to detect abnormal states or sensor faults. 3. Required System Scope A. Reference simulation Implement or integrate a validated finite-difference/finite-element solver for a 1D then 2D heat/Poisson-style problem. Verify convergence against a known analytic/manufactured solution where possible. Generate a parameterized simulation dataset across boundary conditions and physical coefficients. B. PINN Implement PDE residual, boundary and initial-condition losses using automatic differentiation. Compare activation functions, sampling schemes and loss weighting. Use at least Adam plus a second-stage optimizer such as L-BFGS where appropriate. C. Inverse problem Hide one or more physical parameters and estimate them from sparse noisy measurements. Quantify identifiability/uncertainty across sensor counts and noise levels. D. Neural operator Train FNO, DeepONet or a comparable operator-learning model over a distribution of PDE conditions. Evaluate generalization to unseen parameters/boundaries without retraining from scratch. E. Sensors &amp; anomaly detection Compare random, uniform and information/error-driven sensor placement. Inject sensor faults, unexpected sources or changed boundary conditions and detect model-physics inconsistency. F. Digital twin interface Interactive or scripted interface that accepts physical parameters/boundaries/sensor readings and returns field predictions, inferred parameters, errors and anomaly indicators. 4. Mandatory Experimental Program Generate a controlled benchmark grid across unseen parameter values, boundary conditions, sensor counts and noise levels. Compare numerical solver, data-only network, PINN and neural operator on the same cases. Ablate collocation strategy, loss weighting and sensor placement. Run inverse-problem experiments at multiple noise and sparsity levels. Measure out-of-distribution generalization beyond the training parameter range and clearly document failure points. Important: The project is not considered complete when the first model works. The first working version should appear early and then be challenged, measured, improved and re-tested. 5. Deliverables Validated numerical reference solver and dataset generator. PINN implementation with training diagnostics. Inverse-parameter estimation pipeline. Neural operator model with generalization benchmark. Sensor-placement and anomaly/fault module. Digital twin dashboard or reproducible simulation interface. 15-20 page technical report with numerical verification and failure analysis. Final demo and technical viva. 7. Reproducibility &amp; Engineering Standards All experiments must be reproducible from a fresh clone using documented commands and configuration files. Use fixed seeds where applicable and record dataset/model versions, hyperparameters, metrics and runtime for every formal experiment. Training, evaluation and serving must be separated into scripts/modules; notebooks may be used for exploration but are not the final runtime. The final system must expose a repeatable evaluation command that produces machine-readable results (JSON/CSV) in addition to human-readable charts. Use version control throughout the project. Major experimental changes should be visible in commit history. At least one containerized or otherwise reproducible deployment path is required. Document all known limitations and cases where the system should not be trusted. 10. Use of AI Coding Assistants AI tools are permitted and expected. They may accelerate coding, debugging, literature discovery, test generation and documentation. They do not replace experimental ownership or technical understanding. Maintain an AI-use log for significant generated code or design decisions: what was requested, what was accepted, what was changed, and why. You must be able to explain and modify any code you submit during the viva without relying on an AI assistant. Generated metrics, claims, citations and experiment conclusions must be verified against actual runs. Using an existing repository is allowed only when clearly attributed and materially extended; a wrapper around an existing project does not satisfy the brief. The hidden benchmark is designed to test generalization. Optimizing only for the visible development set will not pass. 11. Final Review &amp; Hidden Evaluation After code freeze, the mentor will provide unseen physical parameters, boundary conditions, sparse/noisy sensor readings and at least one hidden fault scenario. The system must estimate fields/parameters and identify abnormal behavior without tuning to those exact cases. Code is frozen before the hidden challenge is revealed. The mentor may provide new inputs, distributions, attacks, failures or operating constraints not present in the public development set. The hidden challenge is scored on measurable system behavior, not presentation quality. Only fixes explicitly allowed by the mentor after reveal may be made; default policy is no retraining or code changes after the final benchmark starts. A short technical defense follows the benchmark and may include live code modification or explanation of unexpected failures. 12.
